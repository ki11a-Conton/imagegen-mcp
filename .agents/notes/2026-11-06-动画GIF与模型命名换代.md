# 决策：动画 GIF 支持与模型命名换代 2.6（2026-11-06）

状态：生效

## 问题

上游 2026-11-04 发布 Images 2.6，新增动画 GIF 生成能力，且明确覆盖所有订阅档位（官方原文
"across all subscription tiers"，free 账号实测可用）。同时 chatgpt2api 服务端的对外模型白名单
已同步换为 2.6 系列。本工具要对齐两件事：模型命名与动图能力。

实测数据（2026-11-06，真实上游 + free 号池）：

- 提示词写明「animated GIF + 帧数」时，上游按要求的帧数出帧：8/10/12/16 帧四组全部兑现。
- 动图尺寸由上游自选（291×437 / 352×355 / 378×250 / 437×387），`size` 参数不起作用。
- 耗时 51~62 秒/张，比静态图（约 35 秒）慢。
- 约 5% 概率被上游内容防护拒绝（`upstream_text_reply`），同参数重发即可通过。
- 模型名与动图无关：所有 `gpt-image-*` 名字都路由到上游 `auto`，出不出动图取决于提示词。

## 决策

- 模型白名单换为 `gpt-image-2` / `gpt-image-2.6` / `-flare` / `-sunburst`，默认 `gpt-image-2.6`。
  服务端仍接受 2.5 老名字（校验放行），但本工具不再暴露。
- 新增 `animated` 布尔参数（顶层默认 + 任务级，规则与其他参数一致）：
  1. 提示词末尾追加固定硬约束（含「不能是静态图片」与缺省帧数区间）；
  2. 忽略 `size`/`resolution`（动图不走本地放大，下发像素没有意义），保留非方形 `ratio` 的构图提示；
  3. 落盘扩展名以字节魔数为准（GIF 识别 0.5.x 已有），新增按 Graphic Control Extension（`21 F9 04`）
     计数帧数，报告在尺寸列带 `NxN 8f`、note 带「动画 GIF 8 帧」。
- 上游回静态图时如实说「本轮回的是静态图，重发一次通常就出动图」，不假装成功。

## 替代方案（否决）

- **透传 `model: "gpt-image-2.6"` 指定动图引擎**：上游 prepare 对任何 `gpt-image-*` slug 都回
  `conduit_token: null`（静默拒绝），锁不住版本。命名只是标签。
- **下发像素让动图变大**：GIF 不走服务端 Lanczos 放大（服务端对动图原样透传），传了也没用，
  还会在返回里造成「尺寸可控」的误导。
- **本地把多帧 PNG 合成 GIF**：上游已能直接出动图，合成路线引入依赖且动效不可控，放弃。

## 影响

- 依赖 chatgpt2api 服务端 2026-11-06 之后的白名单；旧服务端传 2.6 名字会 400，两端要一起升级。
- 帧数与 GIF 宽高解析都是零依赖字节级实现，测试用合成 GIF 与真图样本双口径（与 PIL `n_frames` 交叉验证）。
- 动图单张更慢，README 已提示客户端超时留够；偶发拒绝不自动重试（避免内容政策类提示词白烧额度）。
