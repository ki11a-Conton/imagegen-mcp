# 决策：工具面两个入口，技巧放进查询工具的返回（2026-10-18）

状态：生效

## 问题

原先把所有技巧写进 `create_images` 的 description：批量、folder、name、ratio、Markdown 排版、
耗时预期，一共七八行散文。

实际观察是这些技巧经常没被用上：agent 会略读 description，长描述等价于背景噪音。
同时没有「我想知道怎么用」的入口，`list_models` 只报模型和路径，不回答用法。

## 决策

工具面两个入口，职责单一：

| 工具 | 职责 |
| --- | --- |
| `create_images` | 执行。描述压到两行，只写「什么时候用」与最容易踩的一条 |
| `info` | 查询。返回用法速查 + 连通性 + 模型 + 上限 + 当前输出目录 |

技巧写在 `info` 的返回里，分 `params` / `output` / `display` / `templates` / `pick` 五段：

- `create_images` 的描述末尾直接指向它，形成「不知道就查」的路径。
- 参数级的 `.describe()` 保留一句关键约束，那是 agent 读 schema 时真正会看的位置。
- 返回里的 Markdown 引用每张一行，并排只给一行示例，不强制排版。

## 替代方案（强制）

- 继续把技巧堆在 description：已验证会被略读，写多少都没用。
- 加第三个 `help` 工具：与 `info` 职责重叠，两个查询入口反而增加选择成本。
- 把技巧做成 MCP resource 或 prompt：DSH 侧不一定消费，多一层不可控依赖。
- 在每次返回里附带用法提示：噪音太大，重复任务时会淹没结果。

## 影响

- agent 的决策路径变短：要做就 `create_images`，不会传参就 `info`。
- 技巧的维护点收敛到四处（`PARAMS` / `OUTPUT` / `DISPLAY_RULES` / `DISPLAY_TEMPLATES`），改文案不散落。
- 破坏性变更：`list_models` 改名为 `info`，返回从 JSON 改为可读文本。
