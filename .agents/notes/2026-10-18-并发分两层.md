# 决策：并发分两层，进程级闸门兜底（2026-10-18）

状态：生效

## 问题

并发只按「单次调用」限流时，总量会随调用次数线性放大。

实测：两个调用各带 3 个任务，同时发出后上游在途请求达到 6 路；上游安全线约 4 路，超过就开始 524。

这意味着「N 个 agent 各调 1 次」与「1 个 agent 调 1 次带 N 组任务」对上游的压力不等价，前者的实际风险高得多。

## 决策

并发分两层：

- **单次调用**：自己的 worker 池，`concurrency` 参数控制，默认 3，上限 6。
- **整个进程**：一个在途闸门，`IMAGEGEN_MAX_CONCURRENCY` 控制，默认 4。

闸门包在 `callUpstreamLimited` 里，`runJob` 只能通过它访问上游。
名额释放时直接转交给等待者，`inFlight` 不变，避免惊群。

## 替代方案（强制）

- 只保留单次调用限流：总量随调用次数放大，多 agent 场景必然打挂上游。
- 只保留进程级闸门：单次调用拿到全部名额，一个调用就能吃满，仍会打满上游。
- 让调用方自己算总量：把正确性外推给使用方，多 agent 协作时没人做这个协调。

## 影响

- 两种用法对上游压力一致，可以互换：实测「1 次调用 2 组」与「2 次调用各 1 组」峰值并发都是 2。
- 压力场景（2 次调用各 3 组）在途总量压在 4，不再突破安全线。
- 代价：任务多时总耗时会变长，因为要排队等名额。这是刻意的取舍。
